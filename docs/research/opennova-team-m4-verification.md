# OpenNova 团队 M4：总管值守、团队总览与历史查询

2026-11-08。承接 M1 员工与任务归属、M2 成果验收和 M3 生命周期验证。M4 让总管按明确规则持续观察任务，并通过原任务面板、语音和对话查看真实团队进展。

## 使用方式

打开右侧 Nova 窗口的“任务”页，顶部显示“正在做 / 需要你处理 / 最近成果”。点击条目进入原任务详情；负责人筛选查询整个数据库，任务记录支持加载更多。员工状态、管理员工、任务记录和值守设置均可折叠，没有增加单独的“回复员工”入口。

“总管值守”展示当前提醒和“已知晓”。确认提醒只表示用户已经看到，不会完成、取消、接续或重跑任务。需要补充要求或回答员工问题时，仍通过原对话框或语音表达。

值守默认开启提醒，规则如下：

| 规则 | 默认值 | 触发与处理 |
| --- | --- | --- |
| 临近截止 | 提前 60 分钟 | 有明确 dueAt 的未结束任务进入提醒范围 |
| 已逾期 | 截止时间已过 | 未结束任务显示逾期；不判定执行失败 |
| 等待较久 | 30 分钟 | 持续等待前置条件或事件；旧任务从首次可信观察开始计时 |
| 无新进展 | 30 分钟 | 运行中的任务没有新的真实活动；心跳不算进展，不因此停止进程 |
| 逾期排队提优先级 | 关闭 | 用户明确开启后，仅将逾期且仍排队的任务提高为 high，一次执行并留审计记录 |

时间提醒填 0 表示关闭该类规则，时间范围为 1 秒至 7 天；“临近截止”关闭不关闭“已逾期”。关闭整个值守会解除当前提醒，不改变任务执行。任务 Run、派工版本、截止时间或阻塞原因发生变化时，旧提醒不再适用；重复观察和重启不会重复创建同一提醒。

可直接说：“现在大家都在做什么，有哪些需要我处理？”、“今天完成了什么？”或“资料员这条逾期提醒我知道了”。团队汇总工具使用全量计数，各分组只返回有限条明细，不能把明细页数当成总任务数。执行完成与验收通过分开；“已验收记录”依据当前执行轮与当前成果版本的持久化决定，不表示全部历史文件刚刚重新校验。显示某份成果或使用依赖时仍核对实际证据。

`period=today` 使用宿主本机时区的当日零点：执行完成按当前 Run 的 finishedAt 统计，验收记录按决定时间统计；进行中和待处理仍是当前状态，不受日期筛选限制。不是跨所有旧 Run 的历史工时或审计报表。

## 实现边界

- `tasks/queries.mjs` 负责 SQL 分页、全量计数和调度候选。每 250 ms 调度只读取当前活动/待清理执行、待交接与依赖候选、排队任务。旧 Run 的清理标记不能阻塞新 Run。
- 已结束任务的固定依赖不进入周期扫描；显式查看历史摘要、详情或使用依赖时即时重验来源与成果，保持变更提示，不以缓存掩盖证据变化。
- `task_review_candidate` 由事务内触发器维护并在启动时重建。当前 Run、派工版本和最新 reportId 精确匹配；同 Run 新生成成果仍须重新验收，事务回滚不能丢失候选。
- `team/outbox.mjs` 只查询到期未投递记录，保留接收方回执核对和幂等投递。
- `team/watch.mjs` 通过调度器最多每 5 秒观察一次活动候选；策略、提醒、确认和提优先级动作保存在现有仓库外 SQLite。页面/API 的状态与截止绑定检查能立即排除旧提醒，文件活动的更新最多延迟一个观察间隔。
- `team/overview.mjs` 汇总全量持久状态，只对页面明细读取成果证据。`team_overview`、`team_watch_policy`、`team_watch_ack` 接入原主对话工具通道，策略与确认操作保留用户请求身份、版本检查和动作去重。
- 继续单机串行、前台对话优先、Agent 默认不限执行预算。工作窗口默认不打开，语音停止不取消后台工作。配置、授权、会话、记忆、任务与备份继续在原仓库外位置。

M4 没有增加周期性业务任务、晨会、并行员工、自动改派或任意外部消息触发。这些能力应在后续里程碑单独定义。

## 已完成的验证

- 定向覆盖全量统计超过 50 条、负责人分页、当前 Run/派工/报告绑定、当地午夜、执行与验收时间分离、提醒去重、持久重启、旧版本拒绝、策略回滚和提优先级的明确授权。
- 真实 Bot/Harness 离线集成覆盖原语音请求通道调用汇总、策略、提醒确认；后台真实命令仍运行，重启后设置保留且不重跑已结束执行。
- 真实 Chrome 460×900：128 项任务全量汇总，员工筛选加载全部 67 条、无横向溢出；确认提醒、设置保存、自动重连和原详情导航均通过。重启时仅有预期的 SSE 中断和一次旧 Cookie 401，没有页面脚本错误。
- 真实模型通过转写后的 `source=voice` 入口自主调用 `team_overview`，准确区分 63 项任务、61 项执行完成、31 项验收记录，以及 1 项真实运行和 1 项逾期排队任务。随后自然语言确认提醒，模型重新查询并精确调用 `team_watch_ack`；任务不取消、不重跑，优先级仍为 normal。
- 真实模型场景中的 60 条历史记录为明确标注的合法克隆样本，仅用于全量查询验证，不冒充 60 次真实执行。此次未重新做物理麦克风/TTS 试听；M3 蓝牙真人验收单独保留。

最终全量回归 **650 项 Node + 186 项 Python，共 836 项通过**；相关上游 Bot **517 项通过**。完整构建、`doctor` 和源码独立性检查均通过，源码审计为 independent=true、gitlinks=0。

原统一入口 `pnpm start` 已启动日常实例，健康接口返回 team.version=4，浏览器连接正常，语音客户端未启动。原 3 名成员、12 项可见任务（含管理任务共 17 Task / 25 Run）、25 Job、6 报告、7 验收、6 投递全部保留。升级前后 8 张既有记录表逐行哈希一致，6 个保护文件（原配置、本机连接凭据和记忆）的哈希一致，SQLite integrity_check=ok；新值守策略只新增自己的表，默认不提高优先级。

实际原数据停机备份包含 16,986 个文件、17 个符号链接、8 份数据库，备份校验通过。备份前发现前一宿主留下旧 state.lock：先确认同机原 PID 已退出及端口关闭，再使用 bundled Bot 的 homeLock 协议正常 claim/release，未强删活锁、未重新登录。

## 历史性能实测

使用相同临时 SQLite、M3 基线算法与 M4 算法比较，历史样本包含已验收报告；第二组除源任务外都有已完成的固定依赖。测的是空闲调度中位耗时，不含模型、网络和真实业务操作，也不代表运行中任务可以无限并发。

| 历史 Task 数 | M3 调度 | M4 调度 | 含依赖：M3 → M4 | M4 全量总览 |
| --- | --- | --- | --- | --- |
| 2,500 | 114.753 ms | 0.150 ms | 270.550 → 0.153 ms | 55.951 ms |
| 5,000 | 232.309 ms | 0.146 ms | 530.112 → 0.148 ms | 117.507 ms |
| 10,000 | 481.014 ms | 0.145 ms | 1091.688 → 0.146 ms | 235.414 ms |

全量总览仍随历史规模线性增长，不声称常量耗时；报告与验收关联通过索引查询，每次仅展开所选 6 份明细。回归同时检查查询计划，防止 SQLite JSON 表达式与 TEXT 主键的比较导致相关子查询退化为全表扫描。已投递 Outbox、已结束依赖和待验收候选都有独立覆盖。

复现与数据：`output/team-m4/history-benchmark.{mjs,json,log}`、`overview-benchmark.{mjs,json,log}`。这些本机运行产物不提交仓库。

证据：`output/playwright/team-m4/ui-evidence.json`、`output/team-m4/real-model-evidence.json`；完整模型日志在仓库外 `~/.local/share/opennova/validation/team-m4-2026-11-07T16-22-36.347Z/`。实际原数据备份为 `~/.local/share/opennova/backups/team-m4-20261108-actual/`，保留检查在 `~/.local/share/opennova/verification/m4-production-20261108/`。敏感运行数据不提交 Git。
