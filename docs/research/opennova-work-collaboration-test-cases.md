# OpenNova 工作协作用例

适用日期：2026-10-14。适用版本：根目录 `start.command` 启动的共享 Bot 语音，以及 `http://127.0.0.1:18560/` 网页聊天。

这组用例验证 Nova 能否围绕 OpenNova 工程理解问题、讨论方案、保存成果、编写代码和运行测试，并让用户在语音与网页之间继续同一项工作。验收以实际文件和工具执行结果为准；语音汇报用于确认沟通是否清楚。

用例状态均为**待用户执行**。本文没有执行下述开发任务，也没有创建其测试产物。

## 测试准备

1. 在 Air 启动 Demo；需要代理时填写实际地址：

   ```sh
   /Users/chenzhuoping/Documents/work/project/openNova/start.command \
     --proxy http://127.0.0.1:7897 --device 'MacBook Air麦克风'
   ```

   蓝牙组合改用 `--device 'SRS-XB100' --output-device 'SRS-XB100'`；省略设备参数使用系统默认输入和输出。

2. 打开 [OpenNova 网页聊天](http://127.0.0.1:18560/)，展开“操作记录”。除指定的跨端步骤外，每轮等 Nova 完成后再发送下一条。
3. 在网页粘贴以下初始化指令，让后续语音可以只说“本次测试目录”：

   > 接下来做一次工作协作验收。请在 output/work-collaboration 下新建一个带当前时间、且不与已有目录重名的测试目录，告诉我完整路径。后面所说的“本次测试目录”都指它。可以读取 OpenNova 的实际源码和说明，但新增和修改的文件只放在本次测试目录。测试过程不要提交或推送 Git，不要修改服务配置，不要重启服务，不要把测试信息写入长期记忆。先完成目录准备，等待下一条任务。

4. 确认 Nova 返回新目录，网页与终端显示的转写正确。记下目录，后面用它核对文件。重复整组测试时重新初始化，不复用旧产物。

这是本次验收任务的范围约定，不是文件系统沙箱。实际工程读写与 Shell 权限已经开放。

## W01 熟悉 OpenNova 工程

**对 Nova 说：**

> Nova，先看看 OpenNova 的工程结构和一键启动代码。用一分钟以内解释，语音客户端、Bot、大模型和 Studio 上的 TTS 分别做什么。从我说话到你回答经过哪些步骤？先读取相关代码，只解释，不修改文件。

**应看到：**

- 出现实际的文件浏览、搜索或读取记录；依据应包括启动入口、语音客户端、Bot 接入等相关实现。
- 正确说明 Air 负责拾音、VAD、云端 ASR 接入、Bot 和播放，Studio 负责 Vivian TTS，GPT 负责大模型推理。
- 说明文件和 Shell 工具由 Bot / Harness 执行；语音开发不依赖自动打开编辑器。
- 本轮没有文件写入，语音解释简明，详细路径可以留在网页。

**验收位置：**网页对话和“操作记录”。只有笼统介绍，没有实际读取记录，不算完成本用例。

## W02 分析语音响应问题

**对 Nova 说：**

> 我想优化语音回复的等待时间。请检查当前 Bot 回复和 TTS 播放的代码，找出哪些环节会增加等待，给出两项优先优化建议，并说明需要怎么验证。这里只讨论方案，不改代码，也先不保存文档。

**应看到：**

- 结合代码说明当前 Bot 等待完整答复，再交给后续语音分句处理；不能把 ASR 或 TTS 支持流式直接等同于大模型回复已实时播报。
- 每项建议说明改什么、为什么可能改善，以及怎样测量，例如区分 Agent 完成、首个 PCM 到达和实际播放首声。
- 没有测量数据时，把耗时原因表述为待验证假设；不能断言当前 VPN、TTS 模型或网络就是主要原因。
- 没有修改或保存文件，也没有为了讨论而更改正在运行的服务。

**验收位置：**网页回答及本轮操作记录。此项验收分析依据与任务边界，不要求实测延迟已经改善。

## W03 形成并修订开发任务单

**第一轮对 Nova 说：**

> 把刚才语音等待时间的两项优化建议整理成开发任务单，保存到本次测试目录里的 voice-plan.md。每项写清问题、修改方向、验证方法和优先级。文件最后单独写一段“本轮约束：保留 Vivian 音色和一点五倍播放速度”。保存后告诉我路径，不用把全文念出来。

**应看到：**实际创建 `voice-plan.md`，内容与 W02 的讨论一致，末尾保留指定约束；Nova 直接保存并汇报，无需审批编号。

**第二轮对 Nova 说：**

> 把任务单里第一项的优先级改成 P0，第二项改成 P1，其他内容保持原样。重新读取保存后的文件，告诉我两项优先级和最后一段是什么。

**应看到：**

- 修改仅涉及两处优先级，原问题、验证方法和末尾约束仍保留。
- Nova 重新读取文件后报告实际结果，没有重复追加整份任务单。
- 工具成功保存后，网页可查看文件差异。若使用 Shell 写入，操作记录中查看命令与输出，再要求读取文件核对；当前不会自动为所有 Shell 写入生成差异。

**验收位置：**实际文件、修改记录和重新读取结果。这里验证的是定向编辑与保留已有内容。

## W04 跨端继续同一项工作

**先在网页输入：**

> 为刚才的语音优化任务单补充两条验收条件：分别测试内置麦克风加有线耳机、蓝牙麦克风加蓝牙音响；两种设备都要检查首声等待和插话后恢复。请更新原来的 voice-plan.md，并保留其他内容。

等网页任务完成后，**通过语音追问：**

> Nova，刚才网页里补充了哪两种设备组合？各自需要检查什么？重新读一下任务单，简短告诉我。

**应看到：**

- 网页修改的是 W03 的同一个文件，保留优先级与 Vivian 约束。
- 语音正确答出“内置麦克风加有线耳机”和“蓝牙麦克风加蓝牙音响”，以及“首声等待、插话后恢复”。
- 不需要重新解释工程、目录或任务背景；没有重新创建另一份任务单。

**验收位置：**共享对话、文件内容和语音回答。语音转写错误时先纠正转写，再判断上下文能力。

## W05 开发一个语音研发小工具

这是在真实工程内完成一个有用途的小开发任务；产物放在本次测试目录，不改变运行中的 Demo。

**对 Nova 说：**

> 在本次测试目录里，帮我写一个计算原始 PCM 音频时长的小工具，使用 Node，不安装新依赖。输入字节数、采样率和声道数，固定为十六位 PCM，返回秒数。再写测试并实际运行：九万六千字节、一万六千采样率、单声道应是三秒；四万八千字节、两万四千采样率、单声道应是一秒；十九万两千字节、一万六千采样率、双声道应是三秒；零字节应是零秒。完成后告诉我文件路径、实际测试结果和调用示例。

如语音转写把数字识别错了，可直接在网页补充下面的验收表后继续，不必重新启动 Demo：

| PCM 字节数 | 采样率 Hz | 声道数 | 预期时长 秒 |
| ---: | ---: | ---: | ---: |
| 96000 | 16000 | 1 | 3 |
| 48000 | 24000 | 1 | 1 |
| 192000 | 16000 | 2 | 3 |
| 0 | 16000 | 1 | 0 |

**应看到：**

- 生成实现和测试文件；十六位 PCM 每个采样值占两字节，时长为“字节数 ÷ 采样率 ÷ 声道数 ÷ 2”。处理的是原始 PCM 数据，不把 WAV 文件头计入音频数据。
- 测试明确核对上表中的独立预期值，没有用待测函数自己计算期望结果。
- 实际调用 Shell 执行测试；操作记录中可见命令、工作目录、输出和退出码。测试成功对应退出码 0。
- 不安装依赖，不修改测试目录之外的源文件。报告的测试结果与真实输出一致。

**验收位置：**实现、测试文件及 Shell 操作记录。只生成代码、没有运行测试，不算完整通过。

## W06 补充异常输入处理并回归

**对 Nova 说：**

> 刚才的小工具再加三个异常输入检查：采样率为零、声道数为零、字节数为负数时，都应明确报错。先补充这三个测试并运行，观察当前实现；如果失败，只修复必要的实现，再运行全部测试。保留原来的四个正常输入测试。最后说明最初结果、修改内容和最终结果。

**应看到：**

- 三类输入都有明确测试，验证抛出异常，而不是返回 Infinity、NaN、负时长或悄悄返回 0。
- 如果原实现缺少校验，应有实际失败输出，随后修复并重新执行；如果原实现已满足要求，应如实说明首次测试已经通过。
- 原来的四组数值仍正确。不能通过删除断言、改掉预期值或跳过测试来得到“通过”。
- 实际执行顺序与口头报告一致，不捏造“先失败再修复”的过程。

**验收位置：**测试和实现差异、Shell 执行记录。此项关注接续开发、失败诊断和已有功能不退化。

## W07 停止正在执行的任务

**前提：**本次测试目录下没有 `cancel-marker.txt`；这组测试使用新目录，因此该文件应不存在。

**对 Nova 说：**

> 做一次取消执行验证：通过 Shell 前台运行一个任务，先等待九十秒，时间到了才在本次测试目录创建 cancel-marker.txt。不要提前创建文件，不要转到后台，也不要用独立计时任务代替。

**操作：**

1. 在网页“操作记录”确认对应 Shell 命令已经进入运行状态。
2. 运行约五秒后，在语音终端输入 `/stop` 并回车，或点击网页“停止回复”；任选一种即可。
3. 等任务取消完成后，通过语音说：“检查刚才的命令是否已经结束，以及标记文件是否存在。只检查，不重新执行。”
4. 从原命令开始计时超过九十秒后，再让 Nova 检查一次标记文件，并发出一个普通读取任务，确认还可以继续工作。

**应看到：**

- 实际命令被取消或中断，不仅停止 TTS；若有子进程，也应结束。可依据操作记录和针对该任务的进程检查核实。
- 两次检查中 `cancel-marker.txt` 都不存在，没有超时后继续写入，也没有自动重跑。
- 新请求可以正常处理；先前 W03、W05 的成果仍保留。

取消只停止尚未完成的工作，不撤销已经保存的文件。本用例故意把写入安排在等待之后，才有“取消后不应出现文件”的验收条件。

## W08 水滴硬件方案讨论与沉淀

**对 Nova 说：**

> 我们讨论水滴终端的第一版音频硬件。测试假设是：它负责拾音、播音和实体静音，Agent 和大模型暂时仍在电脑或云端。请读取项目里相关硬件定义，对比单麦克风和双麦克风两种方案，按拾音、回声处理、功耗和开发复杂度整理。明确哪些是文档已有定义，哪些是建议和待确认项。先不做联网器件选型，把结果保存成本次测试目录里的 hardware-audio-options.md。

**应看到：**

- 有读取相关产品或硬件文档的记录；若已有定义与测试假设有冲突，应指出冲突而不是悄悄重写产品定义。
- 生成清楚的对比与待确认问题，明确双麦克风效果依赖阵列间距、算法和实际声学设计，不能直接保证消除同事声音或回声。
- 未提供或未验证的器件规格、续航、尺寸、成本不写成确定数值。
- 保存的是文本设计成果，没有声称已经完成原理图、PCB、CAD 或实际硬件测试。

**验收位置：**所读取的资料、生成文件及语音总结。这项验证硬件需求讨论和文档协作，不验收专业 EDA 工具能力。

## W09 退出语音后继续工作

**操作：**

1. 记下 W03 的任务单路径和 W05 的工具路径。
2. 在语音终端输入 `/quit`，再用相同的一键启动命令进入语音。保持相同 Bot 配置，不修改 `OPENNOVA_BOT_HOME`。
3. 对 Nova 说：

   > 继续刚才的工作。我们本次测试目录在哪里？任务单里保留的音色和播放速度是什么？小工具补充了哪三类异常输入？请读取对应文件核对，告诉我接下来还没做什么。

**应看到：**

- 复用同一 Bot，能找到原测试目录和产物，不重新创建整个任务。
- 正确说明 Vivian、一点五倍播放速度，以及采样率为零、声道数为零、字节数为负数三类异常输入。
- 区分“讨论并保存了优化方案”和“已经修改了运行中的语音链路”，不能把 W02–W04 的方案讨论说成性能优化已经上线。

**验收位置：**历史对话、读取记录及实际文件。本项验证客户端退出后的接续；不等同于重启 Bot 宿主、整机重启或后台作业恢复测试。
