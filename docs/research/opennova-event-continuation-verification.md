# OpenNova 后台任务第三阶段：事件驱动接续

2026-11-05。在既有 Task / Run / Job 和独立 Harness 会话上增加明确规则下的事件接续，不引入 super agent prototype。事件只创建同一任务的新 Run；沿用原会话和独立工作目录，文件仍需审阅后显式应用。

## 使用方式

创建“修改并验证”任务时，可以勾选“测试完成后自动接续”，填写最多 1–5 次，默认关闭。这个快捷选项创建有效期 24 小时的测试接续规则。Agent 使用 `task_check` 将测试或构建提交给后台，然后结束本轮为 `waiting_event`，释放执行队列；检查完成后，按规则把真实退出码和日志尾部交给下一轮。成功可以汇总，失败可以在原任务范围内修复再验证。次数用尽时不再自动接续，也不再向新的模型步骤提供异步检查工具；必要的最后验证可用原来的同步 `task_command`。

已有 Agent 任务的“事件接续”区域可添加规则、启用或关闭规则、暂停或恢复全部自动接续。创建规则默认不启用。规则的来源、处理要求、已接续次数、到期时间、读取错误和事件消费情况可查看；后台验证可以直接打开对应命令任务看日志。

支持四种来源：

| 来源 | 范围与处理 |
| --- | --- |
| 本任务测试／构建 | 仅接收由本任务当前 Run 提交的独立检查结果；一次 Run 只接受一个检查 |
| 指定后台命令 | 精确绑定 Task ID 和 Run ID；显式启用时可导入这次已结束的执行结果；重试命令不会扩展匹配范围 |
| 项目文件变化 | 最多 10 个明确的项目内相对文件路径，1 秒轮询，稳定 2 秒后生成事件；同一规则尚未消费的变化合并为最新一次 |
| GitHub 评论 | 固定仓库和 Issue／PR 讨论编号，允许的作者名单，加 `/opennova` 前缀；每分钟读取一次新评论 |

“暂停自动接续”保留到达的事件，但不会停止已经开始的 Run。要立即停止模型、命令和本任务的独立检查，使用“暂停任务”。暂停任务同时暂停自动接续；手动接续不隐式恢复自动规则，需要另行点击“恢复自动接续”。关闭规则会取消尚未接续的事件，也会暂停由该规则创建但未启动的 Run。已开始的执行需要使用暂停任务停止。

失败、中断、等待用户输入和取消的 Agent 任务需要人工处理，不会仅因外部事件自动恢复。已完成、等待事件或明确恢复自动接续后的暂停任务可以接收事件。过期或额度用尽的规则不能通过关闭再打开重置预算；继续自动处理必须明确添加新规则。

## 文件与 GitHub 边界

文件来源监听原工程，传入有界的内容资料，不把新版本直接覆盖进任务工作区。Agent 自己修改隔离工作区不会产生同一来源的文件事件；应用时依然检查原文件冲突。监听排除 `.git`、依赖与构建目录、`.env*`、`*.local.json`；拒绝符号链接、越界路径和大于 64 KiB 的文件。文本最多传递 2000 字符，二进制只给摘要。每条文件或 GitHub 规则最多保存 200 个事件，达到上限停止该来源。

GitHub 接入使用只读 REST 轮询，不发送评论、推送或部署。公共仓库可以无凭据读取；私有仓库的 token 放在仓库外，默认 `~/.config/opennova/github.token`，也可通过 `OPENNOVA_GITHUB_TOKEN_FILE` 指定。不要把 token 写进规则、任务目标或工程文件；代码拒绝读取工程内的 token 文件。建议只授予目标仓库 Issues 或 Pull requests 的读取权限。

此接口覆盖 Issue 和 PR **讨论评论**，不含代码行审阅评论。只处理启用之后创建的新评论，编辑旧评论不触发；关闭再启用从新的时间点开始，不追溯停用期间评论。固定访问 `api.github.com`，拒绝重定向；最多读取 5 页、每页 100 条、每次响应 1 MiB。超出读取积压上限显示错误，不推进游标；限流或网络失败保留原游标，按退避时间重试。接口依据 [GitHub 官方 Issue comments 文档](https://docs.github.com/en/rest/issues/comments)。

处理要求来自用户配置；事件内的日志、文件和评论作为资料传入，不赋予修改规则、扩大任务范围或发布的权限。沿用第二阶段边界：worktree 是代码协作隔离，不是操作系统沙箱；受监督命令仍以当前用户权限执行。

## 持久化与恢复

`background_event` 保存事实，`background_rule` 保存范围与预算，`background_delivery` 保存消费状态。命令结果与匹配事件一起提交；消费事件、递增次数、创建新 Run 在同一 SQLite 事务提交。事件和投递采用稳定 ID 去重，重启或重复回执不会多建 Run。GitHub 游标与新事件同事务保存；文件基线和去抖状态持久保存。

已经启动但中断的 Run 不自动重跑；未启动的自动 Run 保持队列语义，启动前重新检查规则启用、期限和暂停状态。检查提交被接受但 HTTP 回应丢失时，宿主依据已持久化的子任务恢复等待状态，避免重复提交。没有清理回执时继续阻塞执行队列，防止旧进程和新 Run 同时写文件。

Task / Run 的预算仍按每轮计算，自动规则额外限制最多 5 次接续、最长 7 天。多条规则各自计数，不代表整个 Task 的总 Token 计费额度。单任务最多 50 条规则，其中最多 10 条启用；全局最多 100 条启用。历史规则、工作区和日志保留供核对，本阶段不自动清理。

授权、会话、记忆、规则、事件、任务工作区和日志继续位于仓库外。源码在 `services/bot/tasks/event-engine.mjs`、`event-sources.mjs` 和 `services/bot/web/event-rules.jsx`，通过既有 manager、controls、Agent 插件接入；未引入外部源码链接。

## 验证记录

自动测试使用真实 bundled Harness、原生文件工具和实际子进程，仅替换模型服务。覆盖失败检查 → 修复 → 再检查 → 汇总、同会话与工作区、原工程未变、重复回执与重启去重、事务中途失败回滚、文件去抖合并、暂停杀死独立检查、提交回执丢失恢复、精确 Run 匹配、额度与过期、路径／凭据边界、GitHub 作者与前缀、旧评论与重复读取、停用时尚未返回的轮询，以及 Web 同源 Cookie／CSRF 与内部检查接口不可从网页调用。

完整回归：456 项 Node 测试、186 项 Python 测试通过。日志在本机忽略目录 `output/event-tasks/full-tests.log`。后续修改经过 9 项事件与完整宿主集成回归。

真实模型在临时 Git 工程与独立 Bot 中通过自然语言提交任务、显式启用 2 次接续：首次检查真实退出码 7，事件接续后修复 `sample.txt`，第二次检查真实退出码 0 并输出 `event workflow verified`，最后一轮汇总。三个 Run 共用同一会话和工作区，原工程仍是 `original\n`；后台执行时前台聊天成功。证据为本机忽略目录 `output/event-tasks/real-evidence.json`。

GitHub 读取通过 HTTP fixture 验证，尚未绑定用户的真实仓库或启用日常任务规则；实际使用需指定仓库、编号和作者，私有仓库另配只读凭据。

浏览器在 460 × 900 窗口完成创建任务并启用测试接续、查看三轮结果、暂停自动接续、添加文件规则、观察待接续事件、恢复后进入第四轮等操作。原工程文件事件没有覆盖任务工作目录。页面与任务面板宽度均为 460，无横向溢出；控制台 0 错误、0 警告。证据为 `output/event-tasks/ui-evidence.json` 与 `output/playwright/event-tasks/rules.png`。

最终完整构建通过，`doctor` 的 `build.ready=true`，源码审计 `independent=true / gitlinks=0`。原工程默认入口启动，健康检查确认 `backgroundTasks.version=3 / eventContinuation=true`。首次等待扩展连接超时，扩展重连后再次运行同一入口成功复用服务并取得 Nova 右侧窗口就绪回执；后续 `chat.show` 返回 `completed / created=false`，未要求打开工作窗口，未启动麦克风。
