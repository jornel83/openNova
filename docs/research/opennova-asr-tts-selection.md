# OpenNova ASR 与 TTS 选型建议

日期：2026-10-12。用户试听 Studio 本机样音后，选定 Qwen3-TTS-12Hz-1.7B-CustomVoice 的 Vivian 作为当前 MVP 默认音色，语气保持温柔自然。CustomVoice 独立合成与 Vivian HTTP 流式回传 Air 已通过，默认请求已切换；Base 的克隆合成与流式回传 Air 已通过，留作后续自定义声音克隆。豆包流式 ASR 2.0 已完成 API 与蓝牙麦克风真人试音；Air Silero VAD 已完成双轮样例接入验证。

## 1 需求与推荐组合

OpenNova 当前采用 DeepSeek Harness 与 GPT-6.1 Sol，语音沿用独立 ASR、Agent、TTS 三条链路。部署方向为本地拾音与语音检测、云端 ASR、Studio 常驻 Agent 服务，以及本地 TTS。中文为主、夹杂研发术语，工作协同与日常陪伴共用 Vivian 音色。用户现有约 20 分钟目标声音录音，留作后续自定义声音克隆，不阻塞 Vivian 接入。

| 部分 | 首轮建议 | 选用理由与边界 |
| --- | --- | --- |
| 本地声音处理 | 复用采集端音频框架的回声消除与降噪，Silero VAD 作为语音检测候选 | 持续检测语音，并在外放时保持输入；需要在 Air 与后续水滴硬件分别验证 |
| 云端 ASR，已确定 | 豆包流式语音识别模型 2.0，实时双向流式接口 | 已完成厂商选择；接下来验证中文研发术语、停顿改口、外放环境与真实上传用量 |
| 本地 TTS，当前默认 | Qwen3-TTS-12Hz-1.7B-CustomVoice，Vivian | Studio / MLX 本机样音已获用户选择；温柔自然的聊天语气，已完成 HTTP 流式回传验证 |
| 本地自定义声音克隆 | Qwen3-TTS-12Hz-1.7B-Base | 保留参考录音克隆路线，按后续需要验证真人目标音色 |
| ASR 备选 | Qwen-Audio-3.1-ASR-Flash-Streaming | 保留前期调研记录；仅在豆包实际验证发现明确缺口时重新比较 |
| 云端 TTS 备选 | CosyVoice 3.5 Flash、豆包声音复刻模型 2.0 | 用于桌面 Demo 的过渡基线或本地方案未达标时的备选；尚未接入，不自动切换 |

ASR 继续验证豆包 2.0 的真实场景；TTS 已切换 Vivian，继续验证现场播放与完整对话接入。音色试听选择与实时链路验证分别记录。整体设计见 [整体语音链路技术方案](opennova-voice-pipeline-design.md)。本地 TTS 在 Studio 验证并接入桌面 Demo，Spark 模型实验与训练不纳入首轮。实施安排见 [MVP 开发环境部署方案](opennova-mvp-development-deployment.md)。

## 2 Always On 的实现边界

Always On 的目标是：未静音时持续保持可交流状态，不需要每句话按键或重复固定唤醒词，助手播放时仍可接收用户插话。该体验由以下环节共同实现。

| 环节 | 要解决的问题 | 首轮处理方向 |
| --- | --- | --- |
| 声音采集与回声消除 | 能否持续听到用户，并抑制扬声器播报造成的回声 | 在靠近麦克风的采集端处理，使用实际播放音频作为回声参考；保留实体或界面静音控制 |
| 本地 VAD | 当前是否有人声 | 优先评估 Silero VAD；短时缓存在内存中，保留语音起点前的一小段音频，避免漏首字 |
| 流式 ASR | 用户说了什么 | 检测到候选人声后发送云端，接收中间与最终文本；短暂停顿保留在同一识别任务中 |
| 发言结束判断 | 停顿、思考、改口还是已经说完 | 综合服务端断句与会话上下文；中间转写先展示，确认后的输入才进入工作执行链路 |
| 设备指向判断 | 这句话是否在对助手说 | 首次发起、已有对话和结束交流后分别处理，结合上下文与可用声音线索验证 |
| 插话处理 | 用户讲话时何时停播，如何接收修正 | 接收可信插话信号后本地停播、清空播放队列，取消旧 TTS 并丢弃迟到音频；后台工作任务独立管理 |
| 长时间运行 | 网络断开、服务超时后能否继续交流 | 处理重连、会话轮换、音频时间关系与重复文本，界面明确显示离线或恢复状态 |

Silero VAD 提供 CPU/ONNX 路线，适合作为本地检测候选，但其职责是检测人声，不负责判断说话对象。[Silero VAD](https://github.com/snakers4/silero-vad)

本地 VAD 筛除静音和部分非语音片段；候选人声仍会送往云端识别，Studio 再判断是否应该回应。电视对白、家人交谈和用户自言自语需要专门测试。说话人识别也不能单独证明某句话在对助手说。发言轮次与打断可参考 [LiveKit 轮次处理](https://docs.livekit.io/agents/logic/turns/)，具体框架尚未确定。

本地监听与云端连接分别管理。不能把“Always On”实现为无限累积上下文，也不能假定一个 WebSocket 永不超时。静音立即停止采集；原始音频默认不形成长期记录。外网断开时本地检测仍可运行，云端 ASR 与 LLM 暂不可用；即使本地 TTS 可用，也不等于支持完整离线交流。

## 3 ASR 决策与候选记录

| 候选 | 已确认的接入能力 | 在本项目中的位置 |
| --- | --- | --- |
| Qwen-Audio-3.1-ASR-Flash-Streaming | WebSocket 流式输入输出，支持热词和 Prompt 上下文，可选择近场或远场 VAD；可返回时间信息 | 保留备选，不作为首轮接入前置条件 |
| Fun-ASR-Realtime | WebSocket 流式识别、热词；云端产品与开源 FunASR 工具包需分别对待 | 同平台备选。用于对比识别效果、接入控制与成本 |
| 豆包流式语音识别模型 2.0 | 提供实时 WebSocket 接口、热词与对话上下文接入 | 已选定。使用边说边返回结果的实时接口，不能用说完整句才返回的接口替代 |

阿里云能力依据：[ASR 选型](https://help.aliyun.com/zh/model-studio/asr-model/)、[实时识别指南](https://help.aliyun.com/zh/model-studio/real-time-speech-recognition-user-guide)、[Qwen-Audio 流式 ASR 客户端事件](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events)。豆包依据：[实时语音识别接口](https://docs.volcengine.com/docs/DoubaoVoice/LargemodelstreamingautomaticspeechrecognitionAPI?lang=zh)。

豆包首轮以采集端统一的单声道 PCM 音频接入，账号凭据、资源 ID、音频格式及流式参数按实际开通的实时服务核对。耳机基线与桌面外放分别测试；服务端断句不能直接代替 OpenNova 的对话结束判断。

评估重点是最终语义是否正确，尤其是否丢失“不”“先别”“改成”等修正词。不要为清理口语而提前删除重复、犹豫或改口内容。识别增量发生修订时更新原文本，避免将中间结果重复提交为多条指令。

## 4 TTS 选型与声音克隆

### 4.1 已确定的模型与选择依据

**当前 MVP 默认使用 Qwen3-TTS-12Hz-1.7B-CustomVoice / Vivian。** 用户在 Serena 与 Vivian 的本机同文试听中选择 Vivian，保留温柔、自然、放松的聊天语气。模型版本、语气指令与样音见 [TTS 运行说明](../../services/tts/README.md)。音色选择来自非流式样音；后续 HTTP 流式回传也已通过，两组结果分别记录。

输出语速默认 **1.5 倍**，按用户反馈加快节奏。当前由 Air 对 PCM 做保持音调的流式变速，模型仍按原语气生成；不把倍速视为模型推理性能提升。

模型权重和官方代码采用 Apache 2.0 许可，可本地推理。CustomVoice 面向预设音色，当前通过 `voice=Vivian` 与语气指令生成；Base 支持参考录音克隆，保留为后续自定义音色路线；VoiceDesign 面向文字描述生成音色。不能把 Base 检查点直接配置成 Vivian 预设。[官方模型卡](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice)、[官方代码与许可证](https://github.com/QwenLM/Qwen3-TTS)

### 4.2 后续自定义声音的录音准备与直接克隆

本节仅适用于后续 Base 克隆，不是当前 Vivian 预设音色的接入条件。

先从现有约 20 分钟录音中选取几段清晰、无背景音乐、单人说话且音色有代表性的片段，逐段校对转写；不把全部录音直接拼成一次参考输入。每段参考录音使用同一组测试文本生成样音，比较音色相似度、自然度和稳定性，再固定首版参考片段。

首轮采用 `ref_audio` 与 `ref_text` 的完整参考方式。官方接口允许预先构建并复用 `voice_clone_prompt`，避免每次重复提取同一参考特征；只使用说话人向量的模式可能降低克隆质量，暂不作为质量基线。[官方克隆接口说明](https://github.com/QwenLM/Qwen3-TTS#voice-clone)

工作协同与日常陪伴共用同一音色配置，记录模型版本、参考片段、转写与生成参数。其余录音保留用于补充测试或后续微调。**直接克隆满足要求即可先接入，不把微调作为 MVP 前置条件。** 若相似度、长句稳定性仍不足，再针对问题补录并评估单说话人微调；官方已提供相应流程，但约 20 分钟录音是否足够需由实际数据质量与效果决定。[官方微调指南](https://github.com/QwenLM/Qwen3-TTS/blob/main/finetuning/README.md)

### 4.3 中文体验与 Studio 部署验证

| 验证项 | 测试内容 | 记录与判断 |
| --- | --- | --- |
| Vivian 音色 | 固定预设与语气参数，覆盖正常说话与轻声交流 | 已获用户选择；继续验证不同台词下的自然度与稳定性 |
| 后续目标声音克隆 | 相同文本对比不同参考片段，覆盖正常说话与轻声交流 | 启用 Base 时另行确认相似度、自然度与参考版本 |
| 中文场景 | 工作进度汇报、方案讨论、日常陪伴、中英混读、数字与长句 | 错读、漏读、重复、停顿、语气及音色漂移 |
| Studio 推理 | 模型加载、首次请求、预热后的连续请求及资源占用 | 固定运行环境，记录兼容性、加载时间、内存与推理表现 |
| 实时输出 | 首段文本到首段音频、实际出声、长回复连续播放 | 分别验证音频分块输出与增量文本输入；统计中位数、P95 和播放断续 |
| 打断与资源释放 | 停播、清队列、取消生成、丢弃旧音频、再次发起 | 用户停声与服务停止计算分别记录，确认旧回复不重新播放 |

Mac Studio 是已确定的推理节点，采用 MLX-Audio 与社区转换的 BF16 权重；**CustomVoice / Vivian** 的 HTTP 音频回传与断流后新请求已通过；下一步验证现场音质、连续播放和插话。后端与模型版本见部署方案。既有 Base 流式测试数据继续保留，不能作为 Vivian 的性能结论。

Studio 为日常 TTS 保持模型常驻，并测量与 Agent 工具执行、开发构建并发时的表现。Spark 仅在需要微调时另行接入；训练产物迁回 MLX 后重新验证音色、兼容性与速度。

### 4.4 云端备选

CosyVoice 3.5 Flash 与豆包声音复刻模型 2.0 保留为桌面 Demo 的过渡基线或本地方案未达标时的备选。两者仍需完成实际音色注册、试听及流式接入。云端音色 ID 与本地参考配置分别管理，切换服务需明确选择，不能假定音色相同或自动上传本地参考录音。[CosyVoice 复刻说明](https://help.aliyun.com/zh/model-studio/voice-cloning-user-guide)、[豆包双向流式 TTS](https://docs.volcengine.com/docs/DoubaoVoice/WebSocketBidirectionalStreaming-V3?lang=zh)

## 6 最小验证顺序

1. **ASR 独立基线：** 接入豆包流式 ASR 2.0，使用中文、英文术语、停顿、否定和改口录音，记录正确性、首次出字、最终文本延迟与增量修订。
2. **已选音色与中文体验：** 固定 CustomVoice / Vivian 与本次聊天语气；生成工作汇报、日常交流、中英混读和长句，验证自然度和稳定性。Base 真人声音克隆另行推进。
3. **Studio 实时服务专项：** 验证运行环境、首段音频延迟、连续播放、增量文本、打断停止与资源释放。输出样音、环境配置与测量记录；达到接入要求后再接入完整链路，微调按效果决定。
4. **语音闭环：** 接入 GPT-6.1 Sol 与 Harness，检查回复文字进入 TTS、用户插话、取消和迟到音频丢弃。普通问答与工具任务分别记录端到端延迟；文字工作闭环与 TTS 验证分别推进，语音闭环优先接入 Studio 本地 TTS。
5. **Always On：** 在静音环境、电视背景、家人聊天和自言自语条件下测试首次发起与连续交流，分别记录每小时误回应、明确对助手说话的漏回应和外放回声造成的自触发。
6. **持续运行：** 覆盖数小时运行、网络断开与恢复、服务会话超时、用户静音与恢复，确认无漏首字、重复转写、过期播报和任务误取消；同步记录云端用量与本地资源占用。

豆包 ASR 接入验证与本地 TTS 专项可以独立推进。TTS 首选模型已确定，下一步判断目标声音与实时部署能否满足 OpenNova；依据本项目试听和实际出声、停声记录决定接入，不以公开样音或厂商首包指标代替验证结果。
