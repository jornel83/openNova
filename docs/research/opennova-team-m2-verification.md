# OpenNova 团队 M2：成果、总管跟进与员工协作

2026-11-07。M2 在原有 Task / Run / Job、Bot 身份、独立员工会话上实现。M1 的用户验收已完成；本阶段的软件验证与用户后续实际使用验收分别记录。

## 使用入口

在右侧“任务”页创建 Agent 任务，选择员工，可填写验收标准、前置任务、优先级与截止时间。新员工任务默认启用总管跟进，最多自动返工两次；默认累计预算为 600,000 Token、两小时执行时间，包含员工与管理轮次。总管亲自负责的工作由用户验收，不冒充独立复核。

任务详情新增：

- **成果与验收**：版本化摘要、交付文件快照、来源、真实命令/工具记录及验收意见。打开文件和验收通过是独立操作，均不会自动应用代码或发布。
- **总管跟进**：启用、暂停、恢复、返工次数与累计预算。暂停跟进不等于停止员工的当前执行；需要立即停止时使用任务暂停。
- **待你处理**：员工提问、总管需要用户判断、预算用尽或证据变化。回答和返工绑定任务、Run、派工版本与成果版本，旧页面不能覆盖新结果。
- **优先级与依赖**：前置任务验收通过后固定其成果版本；失败、未验收、员工停用和文件缺失会显示阻塞原因。上游后续变动标记资料过期，不覆盖已经发给下游的副本。
- **交接给其他员工**：先停止旧执行并确认进程清理，再增加派工版本、创建新会话和独立工作目录。只移交交接说明、指定成果和已固定的依赖资料，不复制旧员工的私有会话或记忆。

截止时间用于展示和排队排序，执行超时由独立的时限控制。队列仍然串行；前台对话优先。任务面板提示新结果，不自动打断语音播报。

## 实现位置与数据边界

| 模块 | 职责 |
| --- | --- |
| `services/bot/team/reports.mjs` | 在任务完成事务中保存成果、事件与 outbox；复制固定版本文件，保存校验哈希、命令退出码、日志及来源 |
| `services/bot/team/outbox.mjs`、`delivery.mjs` | 持久投递意图、收件记录核对、失败重试、消费去重 |
| `services/bot/team/supervisor.mjs` | 总管管理任务的排队、预算、版本准入、人工决定优先、有限返工与待处理事项 |
| `services/bot/team/review.mjs`、`management-plugin.mjs` | 只读证据工作目录、结构化验收决定及证据准入 |
| `services/bot/team/assignments.mjs`、`tasks/inputs.mjs` | 清理后改派、依赖循环检查、已验收输入固定、跨员工交接 |
| `services/bot/web/team-results.jsx`、`team-inbox.jsx` | 成果详情、处理记录、管理设置、交接和待处理入口 |

总管管理关联原 chief Bot 身份，使用独立 Harness 会话和可追踪的管理 Task / Run / Job。管理任务不会再次生成员工回报，也不会递归唤醒自己。员工可用的执行权限保持原值；管理会话仅能读取本轮报告和证据，并提交验收决定。

上游 `rt.deliver()` 会触发 Bot 的模型接续，且没有按 exchangeId 的内建去重。本次通过独立管理收件适配器保存 Bot 消息 envelope 与回执，再由管理队列消费；没有把通知投进主语音会话。SQLite 事务与外部收件文件之间使用可重试投递、回执核对和幂等消费，不声称跨两种存储恰好执行一次。

原生事件接续先检查并消费可用事件，总管随后检查当前 Run。两条路径共享当前版本校验和累计预算，避免同时为同一版本创建两个有效新 Run。已启动操作结果不明时不自动重放。

授权、Bot 身份、记忆、任务、报告快照、管理会话与回执均在原有仓库外数据目录。历史任务不自动开启总管验收或补跑；原任务权限不迁移升级。

## 验证记录

最终全量回归通过：545 项 Node 测试 + 186 项 Python 测试，共 731 项。`pnpm build` 成功，`pnpm run doctor` 返回构建 ready，`pnpm audit:sources` 返回 independent=true、gitlinks=0。原目录实例已重启，health.team.version=3、backgroundTasks.version=5，桌面控制连接正常。重启前后 3 名成员、9 项任务、chief ID、配置、客户端连接令牌及记忆文件哈希一致；未启动麦克风或修改授权账号。

本次验证使用隔离临时数据，不把测试员工或测试任务写入日常 Bot：

- 真实 bundled Harness + 模拟模型：首轮不完整交付 → 总管读取证据并要求返工 → 原员工接续补齐 → 总管验收通过。
- 真实模型：读取两项本地数据，输出 `summary.md`，执行文件内容断言并以退出码 0 完成；独立总管读取报告和成果后验收通过。来源文件保持原内容。
- 真实子进程：运行长命令后改派，旧命令 PID 清理后才启动新员工；权限保持，私有记忆与会话隔离。
- 事务/故障：结果事务回滚、消息送达后回执丢失、重启核对、重复动作、过期报告、暂停和额度用尽、原事件接续与总管处理竞争。
- 成果：文件漂移、快照损坏、跨 Run 来源、Git 修改/新增/删除、超过 50 项的截断标记；缺失验证和不可读取的二进制成果不自动验收。
- 实际网页 460 × 900：上游验收释放下游、回答员工问题、交接与新派工版本、历史成果只读、窄屏不横向溢出。

## 当前边界

- M2 提供单机串行的总管管理和明确依赖，不包含晨会、周期日报、并行员工或分布式执行。
- 自动验收依赖可读取的文本成果与实际执行证据；无法核对的二进制文件、大文件或缺失证据交给用户处理，不凭模型声明判定通过。
- 成果快照默认单文件最多 20 MiB、总计 64 MiB、最多 50 个；超过限制明确标为不完整并阻止自动验收。
- “完整执行”仍是已接入工具的执行权限，并非操作系统沙箱。验收通过不会合并 Git、推送或发布。
- 长时间运行、更多故障与模型/设备组合、发布准备继续列入 M3；本次真实模型样例不代替这些后续验证。
