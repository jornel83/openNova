# OpenNova 团队 M2：成果、总管跟进与员工协作

2026-11-07。M2 在原有 Task / Run / Job、Bot 身份、独立员工会话上实现。M1 的用户验收已完成；本阶段的软件验证与用户后续实际使用验收分别记录。

## 使用入口

在右侧“任务”页创建 Agent 任务，选择员工，可填写验收标准、前置任务、优先级与截止时间。新员工任务默认启用总管跟进，最多自动返工两次；单轮步骤、Token、运行时长及员工与总管共用的累计预算默认不限制，可在折叠的预算设置中填写上限；留空表示不限制。总管亲自负责的工作由用户验收，不冒充独立复核。

任务详情新增：

- **成果与验收**：版本化摘要、交付文件快照、来源、真实命令/工具记录及验收意见。打开文件和验收通过是独立操作，均不会自动应用代码或发布。
- **总管跟进**：启用、暂停、恢复、返工次数与累计预算。暂停跟进不等于停止员工的当前执行；需要立即停止时使用任务暂停。
- **待你处理**：员工提问、总管需要用户判断、预算用尽或证据变化。回答和返工绑定任务、Run、派工版本与成果版本，旧页面不能覆盖新结果。
- **优先级与依赖**：前置任务验收通过后固定其成果版本；失败、未验收、员工停用和文件缺失会显示阻塞原因。上游后续变动标记资料过期，不覆盖已经发给下游的副本。
- **交接给其他员工**：先停止旧执行并确认进程清理，再增加派工版本、创建新会话和独立工作目录。只移交交接说明、指定成果和已固定的依赖资料，不复制旧员工的私有会话或记忆。

截止时间用于展示和排队排序，执行超时由独立的时限控制。队列仍然串行；前台对话优先。任务面板提示新结果，不自动打断语音播报。

## 实现位置与数据边界

| 模块 | 职责 |
| --- | --- |
| `services/bot/team/reports.mjs` | 在任务完成事务中保存成果、事件与 outbox；复制固定版本文件，保存校验哈希、命令退出码、日志及来源 |
| `services/bot/team/task-context.mjs` | 为成果固定本任务跨轮提问、用户回答和已送达补充的上下文，记录来源与派工版本 |
| `services/bot/team/outbox.mjs`、`delivery.mjs` | 持久投递意图、收件记录核对、失败重试、消费去重 |
| `services/bot/team/supervisor.mjs` | 总管管理任务的排队、预算、版本准入、人工决定优先、有限返工与待处理事项 |
| `services/bot/team/review.mjs`、`management-plugin.mjs` | 只读证据工作目录、结构化验收决定及证据准入 |
| `services/bot/team/assignments.mjs`、`tasks/inputs.mjs` | 清理后改派、依赖循环检查、已验收输入固定、跨员工交接 |
| `services/bot/web/team-results.jsx`、`team-inbox.jsx` | 成果详情、处理记录、管理设置、交接和待处理入口 |

总管管理关联原 chief Bot 身份，使用独立 Harness 会话和可追踪的管理 Task / Run / Job。管理任务不会再次生成员工回报，也不会递归唤醒自己。员工可用的执行权限保持原值；管理会话仅能读取本轮报告和证据，并提交验收决定。

上游 `rt.deliver()` 会触发 Bot 的模型接续，且没有按 exchangeId 的内建去重。本次通过独立管理收件适配器保存 Bot 消息 envelope 与回执，再由管理队列消费；没有把通知投进主语音会话。SQLite 事务与外部收件文件之间使用可重试投递、回执核对和幂等消费，不声称跨两种存储恰好执行一次。

原生事件接续先检查并消费可用事件，总管随后检查当前 Run。两条路径共享当前版本校验和累计预算，避免同时为同一版本创建两个有效新 Run。已启动操作结果不明时不自动重放。

授权、Bot 身份、记忆、任务、报告快照、管理会话与回执均在原有仓库外数据目录。历史任务不自动开启总管验收或补跑；原任务权限不迁移升级。

## 跨轮问答验收修复（2026-11-07）

原问题：首轮员工询问活动名称，用户通过“待你处理”回答后，员工在下一轮生成成果；独立总管的证据目录仅包含当前轮目标、文件和工具记录，缺少上一轮提问及用户回答，因而误判“无法确认名称由用户指定”。

新成果增加不可变的 `taskContext` 快照，并随 `report.json` 传入独立管理会话：

- 收集本任务此前的实际提问、接续指令和有明确送达回执的补充消息，绑定 Task、Run 与派工版本。不读取员工私有会话或记忆。
- 区分用户、员工、总管、事件、交接和未知来源；历史人工回答通过持久化 review / report / nextRun 关联恢复来源，员工自述不能冒充用户确认。
- 原始提交时间决定用户要求的新旧，送达时间只证明收到；迟送的旧消息不能覆盖之后的明确更正。未送达、送达不明、其他任务或未来轮次记录不进入验收证据。
- 上下文最多 100 条事件、每条 8,000 字符、整体 64 KiB，截断显式标记。历史报告与历史管理证据不回写；修复前报告如需复核，可接续原任务生成新版本。

页面入口保持不变，未新增“回复员工”入口，也不提升执行权限。

验证：全量 554 项 Node + 186 项 Python 测试通过，共 740 项；补充迟送消息边界后，相关 9 项定向测试通过。真实 bundled Harness 覆盖人工回答与接续两条路径、第三轮名称更正、管理会话实际读取上下文与成果、旧快照不变。构建成功，doctor ready=true，源码审计 independent=true、gitlinks=0。

## 执行预算默认不限制（2026-11-07）

新 Agent 任务的模型步骤、Token、运行时长，以及员工与总管共用的累计 Token / 时长，默认均不设置上限。页面将这些可选项收进预算折叠区，默认显示“不限制”；填写数字设置该项上限，留空取消该项限制。累计使用量继续显示，修改总管预算用于后续轮次。最多自动返工两次、测试自动接续默认关闭，继续作为独立选项。

接口和持久记录使用 `0` 表示不限制；预算算术中的 Infinity 不落盘。计时器、模型步骤和 Token 检查只在设有正数上限时启用，SDK 请求将零时限转换为省略超时。有限预算仍检查余额；员工执行、事件接续、总管检查及恢复均遵循相同语义。单次命令和工具连接超时不属于整体执行预算，继续使用原规则。

旧任务保留原有预算及已保存的 Run；不批量取消历史限制。升级前同一提交 ID 的重试兼容旧默认值，不重新创建任务，也不把显式预算变更误当重试。

全量 570 项 Node + 186 项 Python 测试通过，共 756 项；随后提交重试兼容回归 12 项通过。真实 bundled Harness 覆盖零预算下执行 41 个模型步骤、40 次工具调用及超过 200,000 Token，实际计量保留；明确步骤 / Token / 时间限制仍能中止，用户取消后嵌套命令进程清理完成。React 表单测试覆盖默认提交零预算、清空上限、有限值和非法值、历史预算显示。

构建及源码审计通过。原目录实例重启后保留 3 名成员、12 项任务及各任务原预算；配置、连接令牌及记忆哈希一致，原语音客户端保持静音。真实浏览器在 460 × 900 下验证了默认空值、不限制 / 自定义切换、非法值阻止提交、清空恢复不限制，无横向溢出；未向日常数据提交测试任务。

## 当前边界

- M2 提供单机串行的总管管理和明确依赖，不包含晨会、周期日报、并行员工或分布式执行。
- 自动验收依赖可读取的文本成果与实际执行证据；无法核对的二进制文件、大文件或缺失证据交给用户处理，不凭模型声明判定通过。
- 成果快照默认单文件最多 20 MiB、总计 64 MiB、最多 50 个；超过限制明确标为不完整并阻止自动验收。
- “完整执行”仍是已接入工具的执行权限，并非操作系统沙箱。验收通过不会合并 Git、推送或发布。
- 长时间运行、更多故障与模型/设备组合、发布准备继续列入 M3；本次真实模型样例不代替这些后续验证。
