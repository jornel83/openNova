# OpenNova 团队版第一版开发计划

2026-11-06 制定，2026-11-08 更新。状态：M1、通用员工执行能力改造与 M2 已完成并获用户验收。M3 软件、恢复和真人蓝牙验收通过；8 小时观察在约 4 小时后中断，仍待完整重跑。M4 调度查询、总管值守和团队总览已完成，软件、浏览器、真实模型及原工程启动验证通过，见[实施与验证记录](../../research/opennova-team-m4-verification.md)。

目标是在已有 DeepSeek Bot 和 Task / Run / Job 基础上，让用户通过总管安排工作，由总管直接处理或委派员工，并在实时面板查看负责人、进展、成果和待处理事项。第一版不实现晨会、定时日报或晨会归档；总管依据任务事件跟进工作。

## 第一版范围

- 使用现有主 Bot 作为总管，首轮验收配置两名员工。复用 Bot 的身份、角色、会话、记忆与能力模型，不建立第二份员工档案。
- 支持三条路径：总管即时执行、总管负责后台任务、员工承接后台任务。用户明确指定的执行者和后台要求优先。
- 提供员工列表、任务列表、成果详情和待用户处理区域。简单即时操作保留操作记录；后台工作有正式任务卡，负责人也可以是总管。
- 总管接收结果，按验收条件检查，执行有限返工，处理信息缺口，记录需要用户决定的问题。
- 保留现有串行后台队列，前台交互优先。管理轮次也受调度和预算约束；多员工身份不代表多个后台执行进程同时运行。
- 员工职责和擅长方向用于分工，不限制任务场景。新任务默认通用工作模板与完整执行权限，支持已接入的文件、命令、联网和浏览器工具；代码模板使用 Git worktree，通用和资料模板使用普通目录。模板只决定输入与目录准备，工具能力和账号授权单独判断。
- 保留现有配置、主 Bot 身份、授权、会话、记忆及历史任务。新增员工状态、任务目录、通知和验收数据继续位于仓库外。
- 暂缓晨会机制、多员工并行、完整群聊管理界面、复杂动态任务图、多模型路由扩展和分布式部署。

M1 已实现并完成离线、真实模型和界面验证，详见[验收记录](../../research/opennova-team-m1-verification.md)。后续[通用执行能力改造](../../research/opennova-generic-execution-verification.md)也已交付；用户确认第一阶段测试通过，不扩大解释为已经验收所有模型、网站和设备组合。未勾选项目属于后续阶段。

## 现有基础和连接点

| 基础 | 复用内容 | 必须补充的连接 |
| --- | --- | --- |
| `engine/bot/ds-bot/` | 员工目录、主 Bot、角色、会话、个人与团队记忆、消息机制 | 将稳定 botId 绑定任务和执行身份 |
| `services/bot/host.mjs` | 主助手、任务管理器、桌面和语音入口 | 接入团队服务与按角色生效的工具策略 |
| `services/bot/tasks/` | 持久任务、独立会话、命令监督、接续、差异和日志 | 负责人、执行快照、验收、事件回报与管理轮次 |
| `services/bot/requests.mjs` 和 `model-gate.mjs` | 前台请求与模型调用约束 | 为后台管理提供独立、可核验的调用身份 |
| `services/bot/web/` | 任务面板、事件更新、断线后快照恢复 | 员工筛选、成果验收、待决策事项 |

当前已有宿主签发的调用身份、绑定员工的任务会话和逐 Run 的工具调用凭据，后台员工不再依赖活动的前台用户请求。M2 已将这些基础接到独立总管管理会话、可靠回报、验收与有限返工；实现和验证边界见[团队 M2 验证记录](../../research/opennova-team-m2-verification.md)。现有 Bot 原生接口继续通过 OpenNova 认证入口适配，不直接开放整套上游管理接口。

优先在 `services/` 实现适配；确需修改 Bot 上游模块时保持小范围、独立补丁，遵守该目录的 AGENTS.md。继续使用仓库内 Harness、Bot、SIWC，不导入 super agent prototype。

## 执行路径和数据契约

| 用户意图 | 路径 | 记录方式 |
| --- | --- | --- |
| 简单问答、查天气、打开页面、读取短文件 | 总管在当前交互中执行 | 现有请求和操作记录 |
| 明确要求后台执行现成命令或脚本 | 总管持有命令 Task | 记录总管负责人、命令、日志和结果；无需额外启动员工 Agent 分析命令 |
| 多步骤分析、开发或资料整理 | 选择符合能力和工作范围的员工创建 Agent Task | 员工负责人、任务会话、成果和验收记录 |
| 指定员工，或要求总管亲自处理 | 在能力范围内按指定执行 | 指定执行者写入任务；不静默改派 |

是否进入后台与谁来负责分别判断。即时执行途中发现需要长期工作时，用同一个请求关联已完成步骤和新 Task，避免重复操作；如果用户指定执行者缺少能力，说明缺口，不声称已分派成功。

| 数据 | 第一版最少字段或约束 |
| --- | --- |
| 团队配置 | chiefBotId、成员 botId、enabled；保留 Bot 原有姓名、职责和模型字段作为唯一来源 |
| 员工工作配置 | botId、启用状态、擅长方向；工作资源和预算按执行配置处理，擅长方向不决定工具权限 |
| Task | 已有 assignedBotId、supervisorBotId、createdBy、reportTo、assignmentVersion、permission、policyVersion、workspaceMode；后续增加 acceptanceCriteria、priority、可选 dueAt、dependsOn |
| Run | 负责人、角色指令、必要记忆、工具范围、模型与策略版本快照；同一负责人接续恢复原任务会话 |
| 验收记录 | taskId、runId、assignmentVersion、产物版本、reviewStatus、检查证据、意见与验收者 |
| 待处理事项 | 来源任务及版本、问题、处理对象、解决状态与答复；答复定位到原任务 |
| 事件与投递 | eventId、来源 Task / Run、目标 Bot、派工版本、投递状态、消费回执 |

执行状态与验收状态分开；建议验收状态使用 pending、accepted、changes_requested、needs_user。新 Run 或产物变化后，旧验收不自动覆盖新成果。总管自己负责的任务采用明确的规则校验或用户验收，不将自查标成独立复核。

后台执行身份由服务端从 Bot 会话、Run 或内部授权凭据解析，不能从模型提交的 botId 字段直接获取权限。总管管理会话和前台语音会话分开，但关联同一总管身份；管理调用有自己的预算和操作记录。

## 里程碑 2 成果与总管跟进

交付后，员工完成工作会产生可追踪回报，总管可以验收、有限返工和处理依赖，用户在面板直接回答问题或查看成果。

分两次交付，优先使总管能独立跟进一项工作，再增加员工之间的协作：

| 子阶段 | 开发顺序 | 完成条件 |
| --- | --- | --- |
| M2-A 总管跟进闭环 | T5 成果与可靠回报 → T6 总管管理与有限返工 → T8 基础验收和待用户处理界面 | 员工交付 → 总管检查 → 必要时返工 → 验收或提交用户决定，全程留有结果版本和处理记录 |
| M2-B 员工协作与面板完善 | T7 改派和明确前置依赖 → T8 完整成果及待处理视图 | 员工 A 已验收成果能交给员工 B；交接、阻塞、过期成果和用户答复均能定位到正确任务 |

M2-A 首次交付保持串行队列，管理会话与前台语音分离。每任务默认最多两次总管返工；单轮和累计执行预算默认不限制，需要时由用户设置上限，达到手动上限后进入待处理。已有“测试完成后自动接续”与总管返工共用接续准入，不能同时启动两轮。当前成果文件、来源显示和基础面板直接复用。

- [x] 在同一个 SQLite 事务保存任务结果、团队事件与待发送通知；管理进程崩溃不丢失待回报成果。
- [x] 通过 Bot 消息适配投递通知并核对持久回执。采用可重试投递与幂等消费，不承诺跨 SQLite 和 Bot 会话文件的单次原子写入。
- [x] 现有 `rt.deliver()` 不自带按 exchangeId 去重，必须增加接收核对；投递结果不明时核对会话记录，不能只重发同一个 ID。

验收：分别在结果保存、消息投递和回执保存处模拟中断；重启后结果可见，同一结果只产生一次有效管理动作。

### T6 总管事件管理和验收

文件：新增 `team/supervisor.mjs`、`review.mjs`、`team-supervisor.test.mjs`；扩展任务执行准入和事件引擎。

- [x] 提供绑定总管 botId 的后台管理会话，与用户语音会话分离；管理轮次复用可追踪 Run / Job、串行调度和预算控制，不要求 Git 工作区。
- [x] 接收任务完成、执行失败、等待信息和真实超时事件；总管读取已有结果后执行接受、要求修改、回答问题或提交用户处理等结构化动作。
- [x] 验收绑定具体成果版本。存在可执行检查时优先核对退出码、日志、文件或断言；模型意见不能替代缺失的验证证据。
- [x] 配置每项工作的自动处理范围、返工次数和累计预算；用户暂停优先，未知执行结果不自动重试。
- [x] 让任务自身事件接续与总管返工使用同一任务版本校验和接续准入，一次只能有一个有效新 Run；任务仍在自动修复时，总管先观察，不再提交另一轮修复。
- [x] 保留总管动作与理由，停止自动处理后给出明确待处理事项，不继续相互唤醒。

验收：员工提交不满足条件的结果，总管要求一次修正后验收；额度用尽或用户暂停时停止；同时到来的接续和验收动作不会双启动。

- [x] 支持显式指定前置任务，拒绝循环依赖；等待前置任务的已验收成果，固定输入版本后启动下一项工作。
- [x] 已验收上游结果之后发生变化时标记下游资料过期，不悄悄覆盖正在执行任务的文件。

### T8 成果和待处理界面

文件：新增 `web/team-results.jsx`、`team-inbox.jsx` 和对应视图测试；扩展现有任务详情和操作接口。

- [x] 待处理事项支持回答信息、接受成果、要求修改；请求携带任务与成果版本，过期页面操作返回当前状态而不覆盖新结果。

验收：面板完整展示“执行结束 → 待验收 → 需要修改 → 已验收”；打开成果或回答问题能定位到正确任务；无需晨会流程即可完成处理。

## 里程碑 3 运行稳定性与交付验收

## 第一版最终验收场景

| 场景 | 可观察的通过条件 |
| --- | --- |
| 简单语音任务 | 总管直接处理，有实际操作结果，无多余员工派工 |
| 总管后台命令 | 立即返回任务编号，负责人为总管，真实日志和退出码可查 |
| 指定员工执行 | 对应员工持有任务，角色和必要资料正确，其他员工数据未混入 |
| 员工成果与总管验收 | 结果版本、检查依据、接受或返工动作可追溯 |
| 自动处理达到上限 | 不再接续，面板明确显示原因及待用户决定事项 |
| 用户补充或回答 | 写入并接续对应任务，不重放已完成操作 |
| 改派与前置依赖 | 旧进程先退出，旧回报无副作用，验收后按指定成果版本启动后续工作 |
| 面板关闭与重连 | 后台继续执行，重新打开看到一致状态和成果 |
| 宿主重启 | 记录恢复，未知操作等待核对，不重复派工或重复返工 |
| 日常使用回归 | 主 Bot 身份、配置、授权、记忆保留，语音与浏览器原功能正常 |
